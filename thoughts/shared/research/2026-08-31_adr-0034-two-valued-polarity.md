# ADR-0034 — removing `does_not_score`, and what the seeded panel becomes

## Problem summary

ADR-0034 makes judge polarity two-valued: `does_not_score` is deleted, every judge in a
panel carries a weight and can fail the panel, and classification-as-a-service leaves V1.
Two pieces of work fall out and are coupled. The first is mechanical and bounded — an enum
migration, a rewritten CHECK, four collapsed branches in `evaluate.ts`, and the `passed`
null-semantics in the published contract. The second is a product decision the ADR
deliberately left open: three of the four seeded judges (`is-bug`, `is-feature`,
`is-question`) become unexpressible, so the panel that is the README's shop window and
BUILD_SPINE M5's dogfooding tenant has to be **replaced, not edited**. The migration must
land before M5 writes the first annotation FK'd to a `jdv_` (ADR-0003), which is why it is
cheap today and expensive later.

- `packages/db/migrations/0008_model_pin.sql` — the model for a hand-written migration:

  `bun run db:generate`, never hand-written; `migrations.test.ts` asserts file/journal

## Existing patterns and constraints that apply

- **Forward-only migrations, no down (CONVENTIONS "Repo shape", ADR-0006).** Postgres will
  not drop an enum value, so 0009 is: drop the CHECK → cast the column to `text` → `DROP
  TYPE` → `CREATE TYPE` with two values → cast back → `SET NOT NULL` on `weight` → add the
  new CHECK. The CHECK must go first: it names the literal `'does_not_score'`, so it is a
  dependency on the type it would otherwise block.
- **The generation workflow is generate-then-hand-edit.** `bun run db:generate` produces the
  snapshot and journal entry; the SQL is then rewritten by hand for ordering and commentary
  (0008 is the precedent). `migrations.test.ts` also rejects any `$1` placeholder, which
  Drizzle emits when a value is interpolated into a `sql` template.
- **Constraints are database-level, not application-level** (`columns.ts:90-93`): the rule
  must hold when a row arrives from a seed script, a backfill, or a psql session. So
  `weight` becomes a column-level `NOT NULL` — which also flows into Drizzle's inferred
  types and removes the null from `PanelJudge` for free — plus a `weight > 0` CHECK. The
  existing comment about `NULL > 0` evaluating to NULL stops being load-bearing once the
  column itself is NOT NULL, but it is worth keeping the positivity check.
- **Immutable versions (ADR-0003)** are the clock on this work. A `jdv_` cannot be edited,
  so the seeded judges can only be replaced, and every dev database seeded before this
  change holds rows the new enum cannot represent.
- **The seed is idempotent by fixed id with `ON CONFLICT DO NOTHING`.** A stale database
  therefore *keeps* the old judges rather than being corrected — which is already the
  README's documented `docker compose down -v` idiom, and is now mandatory rather than
  advisory.
- **`validateSeededPins` has no escape hatch (ADR-0026).** New judges naming real models
  cost one validating call each at seed time and fail the whole seed if a pin does not
  route. Nothing about the panel's *content* changes that; a different judge count changes
  the cost linearly.
- **`code` judges are not executable until M5** (`evaluate.ts` reports them `failed`), so
  every seeded judge stays `type: 'llm'` regardless of how obviously deterministic it looks.
- **ADR-0032/0033 are accepted and unimplemented, and land at M4.** They add `prompt` and
  `template` to `judge_versions`. This migration is 0009 and precedes them; no conflict, but
  the seed will be rewritten twice, so it is not worth pre-shaping for them.


## Decisions taken in review (2026-09-01)

**D1 — The seeded panel and the M5 dogfooding tenant are separated.** The seed serves two
jobs: it is the only panel a fresh clone has and therefore the example a reader learns the
product from, and it is the fixture the tests run against. It is no longer the M5 annotation
subject. Two reasons, both already in the repo: BUILD_SPINE M5's predecessor states M4's
demo moment as *"the full interviewer flow end-to-end, no seeding scripts"*, so by M5 the
dogfood tenant should be created through the console rather than by `scripts/seed.ts`; and
ADR-0003 freezes every `jdv_`, so a dogfood panel living in the seed can never be improved
by the axial-coding pass at M6 — which is the loop it exists to demonstrate.

**D2 — Nothing this repo emits can serve as the M5 dogfooding artifact.** PRODUCT.md:165
targets ≥ 500 annotated traces. The repo has produced 34 PRs and 44 commits in its lifetime
and its issue tracker is effectively empty. Both candidates considered — PR descriptions and
inbound issues — are an order of magnitude short. This is a new open question against M5 and
possibly against the 500 itself; it is not blocking, because of D1.

**D3 — The seeded panel becomes a voice-alignment panel.** The artifact is AI-generated
writing; the panel judges whether it sounds like the author. Four reasons it beats the three
candidates in the section above:

- **The expert is not optional.** Issue triage has a ground truth reachable from the text,
  which quietly undermines the product's premise that some judgments only an expert can
  settle. Whether a draft sounds like you has no ground truth except you, which is the
  premise stated as a demo.
- **It answers D2 for its own purposes.** The artifact is any AI-generated draft, so supply
  is unlimited and accumulates as a byproduct of ordinary work.
- **PRODUCT.md already requires an SME willing to annotate.** For every other candidate the
  author would be role-playing one. Here he is the only qualified annotator that exists.
- **It is a real M7 target.** Voice is learnable from a few hundred labelled examples in a
  way abstract quality is not, so BUILD_SPINE M7's "published honestly" number is likely to
  be a good one.

It is persona #2 from PRODUCT.md:28 — gating generated output on an expert's judgment, from
inside the generation agent, before it ships — in a different domain. So the *taste* persona
survives untouched and only the *triage* persona and §8's dogfooding commitment are
rewritten.

**D4 — The seeded evaluation carries `context`, and the artifact alone is insufficient.**
Register judgments are undecidable without knowing the channel and the recipient: a Slack
reply to a teammate and an email to a client have opposite correct answers to "is this too
formal". "Over-explaining" likewise depends on what the reader already knows. So the seeded
call sends `{artifact, context}`, which makes it the first thing in the product to exercise
`context` end to end — worth having independently of this panel.

**D5 — The bar for a seeded judge is not the bar for a real judge.** M6 replaces them, so
they do not need to be correct. They need to produce verdicts that can be disagreed with
*precisely*, because the disagreement is the annotation and the annotation is what open
coding reads. A judge that is somewhat wrong is useful; a judge that is vague is not, because
there is nothing to correct. **The seed's own comments must say the four are placeholders**,
so they are never mistaken for a product capability the way the M0 four were.

**D6 — Constraints on the judges, from a first pass over the direction.** Not the taxonomy;
error analysis and axial coding have not happened, and these are the shapes the eventual
judges have to fit.

- *"Reads as AI-written"* is the whole panel asked as one question, which CONVENTIONS
  forbids — a judge assessing several criteria returns a verdict that cannot be measured,
  debugged or attributed. What is recoverable is that the tell is largely **formatting**:
  bolded lead-ins on every bullet, the rule of three, a header every two paragraphs, lists
  in rigid parallel construction. Those are observable, and several are `code`-judge
  candidates at M6 — the triage step demonstrating itself. They seed as `llm` regardless,
  because `code` judges are not executable until M5.
- **Formality and eagerness are calibration axes, not binaries.** Too formal / too casual and
  over-eager / flat each need either two judges or one phrased as a deviation from what the
  context calls for. This is the finding that forced D4.
- **Length and over-explaining are two judges.** Length is a property of the text and nearly
  deterministic. Over-explaining is a property of the text against the reader's existing
  knowledge. Merged, they produce a judge that fires on writing that is long and necessary.
- **Both polarities stay represented** (this closes the old Q5). The panel's secondary job is
  still to make `verdict != passed` visible.

**D7 — How the four get chosen, corrected 2026-09-01.** The first version of this said: run
twenty drafts through eight candidate judges and keep the ones the author disagrees with.
That is backwards by the project's own method. PRODUCT.md step 5 makes the first pass
**deliberately taxonomy-blind**, *"because showing categories up front anchors the expert and
caps the taxonomy at whatever was already imagined"* — and eight candidate judges are a
taxonomy shown up front.

The honest version is open coding and axial coding in miniature, by hand and without the
product: collect roughly twenty AI-generated drafts in the chosen register, write free-text
notes on what is wrong with each, then cluster the notes into four categories. It needs no
code and no panel, so it runs in parallel with P1. It produces the seeded judges and the
project's first real open-coding notes at the same time, which is material for M5, M6 and the
public writeup.

**D8 — Two consequences of a single annotator, recorded rather than discovered later.**
Inter-annotator agreement is uncomputable with one person; judge-vs-human agreement is the
metric, which is what BUILD_SPINE M6 already tracks. And the repository is public while the
artifacts are the author's own writing, so which corpus is public-safe is a decision for
now, not for M8.

**D9 — P1 and P2 are separate branches, confirmed.** The migration is time-boxed by ADR-0003
— it has to land before M5 writes the first annotation FK'd to a `jdv_` — while the voice
panel waits on three unanswered questions. Coupling them would let a design question hold up
a migration that gets more expensive every week. So P1 converts the existing four judges to
scoring polarities purely to have something valid to migrate and test against, and P2
replaces them.

**D10 — The enum values stay `passes` and `fails`.** A rename was raised and declined. It was
raised because the names have now been misread twice: `passed: null` on an informational
judge read as broken (which is part of why ADR-0034 exists), and `passes`/`fails` reads as an
*outcome* when it is a *direction* — it says whether answering `true` is good news or bad
news for what that judge examines, not whether the judge passed. Candidates were
`true_is_pass`/`true_is_fail`, unambiguous and ugly, and `positive`/`negative`, shorter and
less clear. Migration 0009 already drops and recreates the type, so the rename was free at
this moment and costs a second enum migration later; the stakeholder's call is that the
current names stay. Polarity itself is kept rather than eliminated by requiring every
question to be phrased so `true` means pass: models answer "is this defect present?" more
reliably than "is this defect absent?", axial coding emits failure modes whose natural
question is the positive one, and the question is public surface the customer writes and the
annotator reads while correcting the raw `verdict`.

**D11 — Mixed corpus, and the author's voice specifically.** The drafts span email, Slack and
longer documents rather than one register. That choice makes D4 load-bearing rather than
decorative: "too formal" flips sign between a Slack reply to a teammate and an email to a
client, so `context` must name the channel and the recipient or half the panel is
undecidable. And the panel is `pat`'s voice, not a generic "author voice" template — so it is
honestly a single-tenant panel, and the README has to frame it as tenant #1's panel rather
than as something we ship. It also sharpens D8: the corpus is explicitly personal, so which
drafts become public fixtures is a decision at P2, not at M8.

**D12 — Every judge must pass a work-versus-evaluation test, and `needs-human` fails it.**
ADR-0034 draws the line — an agent drafting a reply and calling `is-on-brand` before sending
is evaluation because it gates; an agent receiving a ticket and calling `is-bug` to route it
is work because it produces a fact their system needs — but it applies that line only to
polarity. `needs-human` survived because it happened to carry `polarity: fails` and a weight,
which makes it *expressible* under the new enum, not an *evaluation*. Asked of a raw inbound
issue, it is the second row of that table: their bot routes on the answer.

So ADR-0034's cost section undercounts when it says three of the four seeded judges are
unexpressible. It is four of four — three by polarity, one by this test — though the ADR
reaches the same conclusion by another route when it says the panel *"needs replacing, not
editing"* because *"the artifact it judges is a raw GitHub issue rather than anything a
customer's agent produced."* No amendment is owed; the test is already in the ADR, it was
simply never turned on the fourth judge.

Two consequences. **P2's scope is larger than choosing four judges**: every candidate has to
be checked against this test, not only against polarity, and "is it a failure mode?" does not
answer it — `needs-human` is a perfectly good failure mode of a triage bot and still the
wrong judge for us to run. **And the evaluation form of this judge is the ADR's own worked
example**: the agent's routing decision goes into `context` and the judge asks whether it
misjudges the issue, which is a real failure mode, alignable against an expert, and needs D4.

## Open questions for the human

1. **Which four judges**, after D7's open-coding pass. Blocking P2 only, not P1.
2. **How migration 0009 treats a pre-existing `does_not_score` row.** Recommend: refuse, with
   a named message telling the developer to `docker compose down -v`, rather than deleting or
   converting. Converting means the migration guesses a polarity and a weight, which is what
   0008's own header argues against. Confirm "every database is disposable" still holds — it
   does today, and stops holding the moment M5 writes real annotations.
3. **`weight` nullability in the contract** (ADR-0034's third open question). Two different
   fields share one name: `judge_versions.weight` is configuration and becomes NOT NULL;
   `Verdict.weight` is the normalised share *actually applied* and stays nullable, because a
   judge that was skipped, failed or errored contributed nothing. Recommend keeping the
   contract field nullable with a rewritten description naming the one remaining reason.
4. **M5's dogfooding artifact, reopened by D2** — deferred, and it now has until M5 rather
   than blocking this work.

## Recommended approach (input to planning, not the plan)

Three phases. P1 is unblocked now; P2 waits on open questions 1-3.

**P1 — the mechanical narrowing.** Enum, CHECK, `weight NOT NULL`, migration 0009 with the
loud pre-check; `evaluate.ts`'s five sites; `panels.ts`'s two; the contract prose; and the
tests, deleting the ones whose subject no longer exists rather than bending them. Retarget
`constraints.test.ts`'s "not even representable" test at `does_not_score` — a permanent guard
that the value never comes back. Verification is `bun test` plus a `down -v` boot proving a
fresh database migrates and seeds clean. **The existing four judges stay in the seed through
P1**, converted to scoring polarities purely so the migration and the tests have something
valid to run against; they are replaced wholesale in P2.

**P2 — the voice panel.** **Every judge P1 leaves behind is deleted here, `needs-human`
included** — it survives P1 only because a panel with no judges makes `evaluate` throw
`NOT_FOUND`, and it fails the work-versus-evaluation test in D12. Nothing carries over: the
artifact becomes AI-generated writing, so a judge about GitHub issues has no reading under
the new panel. Four judges over the existing three model variables, mixed polarity, at least
one `required` veto, all `llm`, commented as placeholders per D5. The
seeded call gains `context` per D4, which means the request fixture and the README curl both
change shape. Weights and threshold chosen so the README's example produces a legible result
— and because the fake provider derives verdicts from a hash of the call, the example
artifact is picked *after* seeding by running it, never guessed. New `jud_`/`jdv_` seed
labels and a new panel slug; `relations.test.ts` follows.

**P3 — the prose.** CLAUDE.md, CONVENTIONS, PRODUCT (the triage persona, §5.2's polarity
bullet, §7's 500-trace metric, §8's dogfooding commitment), README (persona, seeded-panel
section, pinned-endpoint table, span tree), BUILD_SPINE M5 (the prerequisite paragraph
becomes a record of what landed, plus D1 and D2). Worth one pass rather than being smeared
across P1 and P2: the same sentence is restated in five places, and getting one of them wrong
is how the product ends up saying two things again.

One branch and PR per phase, per CLAUDE.md.
