- 2026-08-24T03:10Z [pat] **Primary keys are generated at insert by Drizzle's `$defaultFn`, and stay prefixed ULIDs rather than becoming UUIDs** — over passing `newId()` at every call site (the status quo), over a Postgres-side `gen_random_uuid()` default, and over a plpgsql ULID generator — because the two halves of "should ids be automatic" have different answers. Generating them automatically is worth it: an insert becomes `{ slug, name, orgId }`, and `drizzle-kit generate` confirms it emits no SQL, so it costs no migration. Moving to UUIDs is not, and the reasons are concrete rather than aesthetic: the id is public contract (it appears in `/v1` paths and in every response body, so CONVENTIONS makes changing it a new API version), the prefix is what makes an id self-describing in a log line or a support ticket and is what the branded types key off so a `pnl_` cannot be passed where a `jdv_` belongs, and ULIDs sort by time — which on `traces`, the highest-volume insert table in the system, is the difference between appending to a B-tree index and scattering page splits across it under load, a cost that would first show up at M2. `$defaultFn` was chosen over a database-side default specifically because a database default cannot be known until the INSERT returns, and an evaluation wants to mint its `tr_` id at the *start* so the request logger can bind it before the row exists (CONVENTIONS "Logging"); a default that is only a default keeps both doors open, and a test asserts an explicit id is still accepted. Two costs accepted and recorded rather than discovered: the default belongs to the query builder, so raw SQL — the seed, any future backfill — bypasses it entirely, which is why the per-table prefix CHECK constraint remains the actual guarantee; and `newId()` falls back to `Date.now()` rather than the injected `Clock` (D-H), which is a small inconsistency judged acceptable because nothing asserts on an id's timestamp. A plpgsql ULID generator would close the raw-SQL gap properly and was rejected: it duplicates the implementation in a second language that then has to stay in sync, and the CHECK constraint already rejects the malformed ids that actually matter. Applies to the eight tables with prefixed primary keys; better-auth's four keep the ids it mints itself, and the three composite-key join tables have no surrogate key. (M0-P3)

- 2026-08-24T04:40Z [pat] **Which panel version is live is a POINTER on `panels`, not "the highest version number"; judges deliberately get no such pointer** — over resolving the live version as `max(version)`, and over an `is_current` flag on the version row — because version order is history and activation is a separate fact, and conflating them removes two things a customer wants immediately.
