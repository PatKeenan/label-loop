- 2026-08-21T01:37Z [pat] **The response envelope carries `request_id` (the W3C/OTel execution id), and `trace_id` is reserved for the `tr_` ULID of a stored classification row** — over a single `trace_id` field meaning both, and over putting the `tr_` id in the envelope — because "trace" already means two unrelated things here: the observability industry's timing breakdown for a request, and our product's saved classification (PRODUCT.md 5.4, the trace explorer, the object SMEs annotate). The two objects differ in every dimension that matters: the execution record covers all traffic and expires with backend retention, while the classification record exists only for classify and is permanent. The failure path is what settled it — if the envelope carried the `tr_` id, a request that 500s before persisting would have no id to return, which is exactly when a caller most needs one; the execution id exists from the moment the request arrives, so it is the only candidate that survives failure. A collision (`trace_id` at envelope level meaning something different from `trace_id` inside `data`) was rejected outright as a documentation and integrator hazard. The `traces` table stores both ids so a business record joins to its spans, one-directionally bounded by the tracing backend's TTL. CONVENTIONS.md amended in five places (envelope, id rules, idempotency, logging, data rules); recorded as ADR-0010. (M0/M1, ADR-0010)

- 2026-08-21T01:51Z [pat] **Two Postgres roles (migrator for DDL, app for DML) land in the first M0 migration, and `audit_events` is created at M0 — empty, with its `REVOKE UPDATE, DELETE` already in place and a test proving it** — over deferring role separation to M8 with the audit log, and over creating the roles at M0 but the table later — because role separation touches every environment (local compose, CI, Railway) and every migration written between now and M8, so retrofitting it means re-granting across all existing tables and changing connection config everywhere, at the same moment Stripe billing is being built. - 2026-08-24T03:10Z [pat] **Primary keys are generated at insert by Drizzle's `$defaultFn`, and stay prefixed ULIDs rather than becoming UUIDs** — over passing `newId()` at every call site (the status quo), over a Postgres-side `gen_random_uuid()` default, and over a plpgsql ULID generator — because the two halves of "should ids be automatic" have different answers. Generating them automatically is worth it: an insert becomes `{ slug, name, orgId }`, and `drizzle-kit generate` confirms it emits no SQL, so it costs no migration. Moving to UUIDs is not, and the reasons are concrete rather than aesthetic: the id is public contract (it appears in `/v1` paths and in every response body, so CONVENTIONS makes changing it a new API version), the prefix is what makes an id self-describing in a log line or a support ticket and is what the branded types key off so a `pnl_` cannot be passed where a `jdv_` belongs, and ULIDs sort by time — which on `traces`, the highest-volume insert table in the system, is the difference between appending to a B-tree index and scattering page splits across it under load, a cost that would first show up at M2. `$defaultFn` was chosen over a database-side default specifically because a database default cannot be known until the INSERT returns, and an evaluation wants to mint its `tr_` id at the *start* so the request logger can bind it before the row exists (CONVENTIONS "Logging"); a default that is only a default keeps both doors open, and a test asserts an explicit id is still accepted. Two costs accepted and recorded rather than discovered: the default belongs to the query builder, so raw SQL — the seed, any future backfill — bypasses it entirely, which is why the per-table prefix CHECK constraint remains the actual guarantee; and `newId()` falls back to `Date.now()` rather than the injected `Clock` (D-H), which is a small inconsistency judged acceptable because nothing asserts on an id's timestamp. A plpgsql ULID generator would close the raw-SQL gap properly and was rejected: it duplicates the implementation in a second language that then has to stay in sync, and the CHECK constraint already rejects the malformed ids that actually matter. Applies to the eight tables with prefixed primary keys; better-auth's four keep the ids it mints itself, and the three composite-key join tables have no surrogate key. (M0-P3)

- 2026-08-24T04:05Z [pat] **A contributor keeps earning from a judge that is still in use after they leave the org; contribution therefore attaches to the person, not to their membership** — over ending royalties at the exit interview, and over an explicit "judge ownership group" holding multiple named owners — because the work is in the artifact whether or not the employment continues, and a royalty that stops when someone leaves is a bounty with extra steps, which removes the reason an SME would treat annotation as an asset rather than as labour. This resolves the open question PRODUCT.md had carried parked under "Contributor revenue share". The **ownership group was considered and rejected as the wrong shape**, not as a bad instinct: PRODUCT already specifies attribution as "a contributor's share of the reliability-weighted annotations included in a shipped training set" — mechanical, not causal — so the set of people a judge owes is *derivable* from an event log (annotations carrying `annotator_id`, plus alignment sessions recording who ran them) rather than declared. The test applied was the one this project has used three times before — *what would this store today that cannot be reconstructed later?* — and for a group the answer is nothing, whereas for `created_by` it is an authorship event that happens once and is then unrecoverable. What the group **did** surface and the current model does not express is negotiated contractual splits (an org agreeing 60/30/10 with three experts, which no annotation count produces); that is real, belongs downstream of the mechanical ledger, and is M8 billing rather than M0 schema. - 2026-08-24T04:05Z [pat] **`created_by` references `user` with `ON DELETE RESTRICT`, and users are anonymised rather than hard-deleted** — over referencing `org_members`, over `ON DELETE SET NULL`, and over deriving authorship from `audit_events` — because each alternative destroys the evidence the decision above depends on. `org_members` cascades from both `orgs` and `user`, so authorship pointed at membership vanishes the moment someone leaves, which is precisely the case that has to survive; the org is reachable through the row's own parents anyway, so pointing at membership would also store the tenant twice and let the two copies disagree. `SET NULL` is subtler and worse: it destroys a payout claim through a cascade rule rather than through a decision, so the deletion looks routine and the loss is silent. RESTRICT makes the invariant explicit and fails loudly, which forces the real answer — anonymise the user, keep the row — and that is also what erasure actually requires (scrubbing personal data, not dropping the record), so the ledger and the right to erasure do not have to be traded against each other. `audit_events` cannot substitute: it ships empty with M8 populating it, so anything created before then would have unrecoverable authorship, and "created by Sarah" wants to be a column read rather than a scan for a matching subject id. The column is nullable because the seed creates rows with no human author, and once the `manage` key scope lands (PRODUCT 5.1) a `created_by_key_id` column can be added with NO backfill, since no key-authored row can exist before the scope does — which is why the polymorphic `actor_type`/`actor_id` shape `audit_events` uses is not needed here. Applies to `panels`, `panel_versions`, `judges`, `judge_versions`, `api_keys`. Deliberately NOT applied to `orgs` (created at signup, circular with the user) or `org_members` (an invitation is an audit event, and there is no invite flow until M4). Also distinguished in passing and worth keeping separate: **contribution** (who is owed, permanent, per person) versus **stewardship** (who maintains a judge now, gets its drift alert, runs the next re-alignment — transfers when someone leaves). Fusing them is what made the ownership-group idea look necessary. Stewardship is M4+ and unbuilt. (M0-P3)

- 2026-08-24T04:40Z [pat] **Which panel version is live is a POINTER on `panels`, not "the highest version number"; judges deliberately get no such pointer** — over resolving the live version as `max(version)`, and over an `is_current` flag on the version row — because version order is history and activation is a separate fact, and conflating them removes two things a customer wants immediately. Rollback becomes impossible: reverting to v1 after v2 exists would mean copying v1's configuration forward into a new v3, which is a different fact recorded as the same shape. And a draft becomes impossible: a new version starts judging live traffic the instant it is inserted, with no way to prepare and review it first. The foreign key is **composite** — `(panels.id, panels.current_version_id) → panel_versions(panel_id, id)`, backed by a `UNIQUE (panel_id, id)` — because a plain reference to `panel_versions.id` would happily let a panel activate a DIFFERENT panel's version: the row exists, so the constraint is satisfied, and panel B would quietly serve panel A's judges. Verified against Postgres: a null pointer is allowed (a composite key with any NULL is unenforced under MATCH SIMPLE, which is what makes the column nullable for a panel that has no version yet), pointing at its own version succeeds, pointing at another panel's is refused with 23503. **Judges deliberately get no pointer**, and the asymmetry is principled rather than an oversight: the serving path is panel → current panel version → `panel_version_judges` → judge versions, so a judge's own "current version" is never consulted at evaluation time, and a judge version not referenced by any `panel_version_judges` row is already a draft by construction. The panel version is the unit of activation; the judge version is a component it pins. **Cost accepted and named:** a pointer that slides leaves no trace, so where `max(version)` made a rollback visible as a new row, this one is invisible unless the move is audited — which makes recording activation changes an M8 `audit_events` obligation rather than a nice-to-have. (M0-P3, ADR-0003)

- 2026-08-24T04:40Z [pat] **`REVOKE UPDATE, DELETE ON panel_versions, judge_versions FROM labelloop_app` — immutable versions become a database guarantee rather than a convention** — over leaving `audit_events` as the single deliberate exception the plan specified — because they are the same class of claim and deserve the same class of enforcement. Until now "editing creates version n+1, never mutates" held for two soft reasons: no code did it, and there is no mutable column on the row to update. Neither survives a bug, a maintenance script, or anyone holding the app credentials, and `UPDATE panel_versions SET threshold = 0.9` would have been accepted. The whole eval story is agreement plotted per immutable version, so a threshold or rubric that can move underneath a timeline makes every timeline suspect and "aligned at kappa 0.81" loses its anchor. Two objections were tested before committing rather than reasoned about. **Cascading deletes still work** — a referential action runs with the privileges of the table owner, not the caller, so deleting an org still cleans up its versions even though the app role cannot delete them directly; this was the one that could have made tenant deletion impossible. And **activation still works**, because the pointer decided above lives on `panels`, which keeps UPDATE — an `is_current` flag on the version row would have been incompatible with this migration, so the two decisions only compose because of how the first one was shaped. Cost accepted: a column that legitimately mutates later, such as `retired_at` or a notes field, needs a migration to re-grant, which is the correct amount of friction for reopening this. (M0-P3, ADR-0003, CONVENTIONS data rules)
